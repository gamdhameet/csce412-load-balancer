Design proposal

Load balancer simulation

A clock-driven model of incoming web requests, two job types, a request queue, and a server pool that grows or shrinks with demand.

The configuration determines task lengths, arrival rate, scaling interval, and blocked address ranges. Generated requests first pass through the IP filter. The switch then sends each allowed request to the processing or streaming queue. Idle servers take the oldest waiting request from their own queue. Each clock tick advances active work; periodic checks add or remove one server in each pool as queue depth changes. The final report combines both pools and keeps their statistics separate.

02

Data model

Request

One unit of work. Stores source and destination IP addresses, processing time in clock cycles, and the job type: P or S.

WebServer

Holds at most one active request. Tracks its remaining processing time and reports when it becomes idle.

LoadBalancer

Owns a FIFO request queue and a pool of web servers. Assigns waiting work, advances active work, and changes server count after a cooldown.

Switch

Routes admitted requests to the processing or streaming load balancer and keeps their statistics separate.

03

Clock and capacity rules

Start

Read the configuration and user inputs, create the initial servers, then fill the starting queue to 100 accepted requests per server.

Advance

On each tick, complete finished work, assign queued work to idle servers, and add new requests at randomized times.

Scale

After a configurable cooldown, remove one idle server when the queue is below 50 requests per server, or add one when it exceeds 80 per server. Keep at least one server per balancer.

Report

Quiet mode prints start and end summaries. Verbose mode also records arrivals, assignments, completions, firewall rejections, and scaling events.
